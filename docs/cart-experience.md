# Carrito Bakatá

La plantilla page-bakata-cart se selecciona por el ID configurado de carrito (no por slug) mediante page_template_hierarchy. Conserva el contenido de la página WordPress y el bloque Cart de WooCommerce; también permite contenido clásico existente sin sustituirlo. No modifica la página almacenada ni introduce carrito, sesiones, inventario, cupones, impuestos, transporte o totales propios. Incluye una navegación real de regreso a la tienda y un landmark main. CSS acotado a bk-cart, tokens del Design System, estilos para productos, cantidades, precios, descuentos, campos, resumen y CTA hacia checkout. Se respetan estados, mensajes y responsive nativos.

QA ejecuta Chromium y axe a 320/768/1440 px con sesiones aisladas y bloquea las solicitudes HTTP del navegador a otros orígenes. Ese bloqueo no restringe el tráfico del servidor ni garantiza bloquear WebSockets. Comprueba estado vacío, enlace a tienda, adición desde homepage, incremento/decremento, subtotal, rechazo visible de un código sintético aleatorio sin cambios en artículos, cupones ni totales, cupón fijo de prueba 5000 COP, total del servidor, persistencia tras recarga y eliminación del cupón conservando el artículo, restaurando el total y retirando su control visual. Verifica el enlace al checkout (sin navegar a él), retirada del artículo y regreso al vacío. Las condiciones de Store API tienen timeout y se consultan hasta observar el estado esperado. El cupón se crea solo en el entorno desechable, después de las pruebas anteriores. No se crean pedidos, no se publican promociones ni se configuran pasarelas. Los tests asumen el bloque Cart predeterminado y la configuración de impuestos/envíos de CI.

Antes de ejecutar las fixtures es obligatorio comprobar que WordPress **y su base de datos y volúmenes** pertenecen a una instalación aislada y desechable, sin datos reales. La bandera `BAKATA_CI_FIXTURES=1` y la comprobación del host `localhost` son salvaguardas adicionales, no prueban que la base de datos sea desechable ni protegen una instalación real accesible localmente.

Pendiente: ejecución en CI de los nuevos escenarios, revisión de capturas, cantidades máximas/stock concurrente, cesta con variantes múltiples, impuestos/envíos configurados, sesión autenticada, compatibilidad visual de carrito clásico, localización es_CO y checkout de sandbox. No se establece una promesa de envío ni se cambia ningún ajuste comercial de Lightsail.

Una ejecución local anterior a la comprobación visual de retirada pasó en Docker desechable con WooCommerce 11.3.1 y Chromium a 320/768/1440 px, junto con las comprobaciones existentes de accesibilidad y carrito. El entorno utilizó fixtures sintéticos; no se navegó al checkout ni se efectuaron pagos. Los informes y capturas de esa ejecución quedaron en la copia temporal `C:\Users\Usuario\AppData\Local\Temp\opencode\bakata-cart-qa-20261127\previous-cart-reports\` (no se versionan y pueden eliminarse).

La ejecución local posterior, incluida la comprobación visual de retirada, también pasó en esas tres resoluciones. Su resumen y capturas están en `C:\Users\Usuario\AppData\Local\Temp\opencode\bakata-cart-qa-20261127\qa\reports\`; son evidencia temporal, no versionada.

## Corrección de QA del cupón
La ejecución 45814268878 validó vacío, alta y cantidades en 320/768/1440 px, pero falló al abrir el panel de cupones. El componente Panel de WooCommerce 11.3.1 utiliza Ariakit con `render={<div />}` y rol de botón, no una etiqueta button. Se busca el control por rol y nombre accesible del entorno CI, se comprueba aria-expanded y se espera el campo específico. Se conserva la aplicación a través de la interfaz y la validación del descuento y total mediante Store API. Se añade diagnóstico de controles del panel. No cambia la lógica del carrito ni se desactivan pruebas. Pendiente nueva ejecución.

## Prevención de reenvío del POST
La ejecución 45814974467 confirmó la aplicación de un cupón de 5.000 COP y los subtotales esperados, pero al recargar la cantidad pasó de 2 a 3 en las tres resoluciones. La forma de homepage enviaba POST directamente a la URL del carrito sin exigir redirección; WooCommerce puede devolver el documento en la misma petición. Se incorpora el marcador de presentación bakata_cart_redirect y el filtro público woocommerce_add_to_cart_redirect, que WooCommerce ejecuta tras añadir correctamente el artículo. El destino es exclusivamente wc_get_cart_url(), no una URL proporcionada por el cliente. No se modifica la opción global de WooCommerce, ni la validación de inventario/cupones, ni la conducta de otros formularios. QA exige una navegación POST→302/303→GET y una recarga GET, conservando la verificación estricta de cantidad 2, cupón y total tras recargar. Causa inferida del comportamiento reproducible y del código nativo; pendiente confirmar la corrección con CI. La ficha individual tiene un flujo separado, probado manualmente con simple y variante en entorno desechable; véase [detalle y límites](product-detail.md#recarga-tras-añadir). Esa prueba todavía no se ejecuta en CI.

## Reflow móvil del carrito
La ejecución 45816154201 confirma POST/redirect/GET, cupón, persistencia de dos unidades y enlace al checkout en todas las resoluciones; 768 y 1440 también superan axe y eliminación. A 320 px se detectaron 59 px de overflow con carrito lleno. El CSS nativo usa tracks fijos y un track implícito en filas estrechas. Se acotan las columnas, se asigna explícitamente imagen/producto/total, se permite envolver controles de cantidad y etiquetas del cupón, y se limita el ancho de resumen y filas. No se oculta overflow ni se recortan acciones. El elemento exacto que originó el desbordamiento no quedó registrado en la ejecución anterior: es una corrección de reflow basada en el código y se añade evidencia geométrica JSON (bounds y estilos) al chequeo obligatorio. Se conserva el límite original de 1 px y auditoría axe. Pendiente CI.
