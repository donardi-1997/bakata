# Infraestructura de desarrollo

Lightsail `bakata-dev-2gb` (us-east-1a, Ubuntu 24.04, 2 GB RAM), IP estática 98.86.5.107. Spaceship resuelve dev.bakata.store; no modificar el dominio de producción. Nginx TLS termina HTTPS; WordPress solo escucha en 127.0.0.1:8080; MariaDB no publica puertos. Docker y Nginx arrancan automáticamente, SWAP 2 GiB con swappiness 10. SSM híbrido permite administración saliente HTTPS.

## Reconstrucción (Ubuntu limpio)
1. Actualizar Ubuntu, instalar Docker Engine + Compose, Git, Nginx, Certbot, apache2-utils, UFW. Crear SWAP persistente. Registrar SSM con rol limitado y activación de un uso. No guardar código de activación.
2. Clonar repositorio como ubuntu en /home/ubuntu/bakata, crear .env con secretos locales, chmod 600, configurar WP_URL=https://dev.bakata.store. Ejecutar bootstrap. Conservar volúmenes.
3. DNS A dev hacia IP estática; firewall AWS 22/80/443 únicamente. Crear /var/www/letsencrypt, instalar infra/nginx/bakata-acme.conf como sitio temporal bakata-dev, habilitarlo, validar nginx -t y recargar. Emitir certificado con certbot certonly --webroot -w /var/www/letsencrypt -d dev.bakata.store.
4. Crear /etc/nginx/.htpasswd-bakata con htpasswd -cB; root:www-data, 640. Usar contraseña distinta de WordPress.
5. Con una sesión SSH y SSM de respaldo, ejecutar sudo bash scripts/apply-host-hardening.sh; revisar salida y probar nueva conexión SSH. El script presupone Ubuntu y el subdominio de desarrollo, no sirve para producción. UFW permite 22/80/443; no publicar otros puertos Docker porque Docker puede eludir UFW.
6. Ejecutar sudo bash scripts/harden-wordpress.sh. Validar curl HTTP 301, HTTPS 401 sin credenciales, 200 con credenciales, certbot renew --dry-run. Verificar home/siteurl, y acceso admin. No cambiar URL de una instalación existente sin comprobar ambos valores.

## Despliegue
El script scripts/deploy-dev.sh está diseñado para instalarse como /usr/local/sbin/bakata-deploy-dev (root:root, 0755) desde un commit revisado. Recibe SHA exacto, exige main limpio, fast-forward, bloqueo de concurrencia, verifica servicios y preserva volúmenes. No aplica hardening de host automáticamente ni ejecuta bootstrap sobre una base existente. No incluye rollback automático: un cambio puede incluir migraciones irreversibles; respaldar antes de cambios de datos. Un fallo requiere inspección y corrección. El despliegue de código de main mediante Docker equivale a confiar en sus contribuidores con privilegios de host. Proteger main y revisar cambios antes de habilitar CD automático.

## Secretos y operaciones
No versionar .env, htpasswd, certificados, claves privadas, dumps, activaciones SSM, archivos wp-config.php ni datos de clientes. El backup local de hardening está en /root/bakata-hardening-20261126-043900/ (contiene configuraciones sensibles, no es backup completo). Mantener SSH por clave hasta verificar un acceso alternativo. Pendiente: protección contra abuso, restricciones SSH según origen, backups externos con prueba de restauración, escaneo de imágenes y alertas. No confundir noindex con control de acceso.

## CD mediante OIDC (deshabilitado por defecto)
Se usa el proveedor GitHub OIDC existente con audiencia sts.amazonaws.com. El documento SSM Bakata-DeployDev v1, versionado en infra/ssm, llama al wrapper instalado como root y solo acepta un SHA hexadecimal. Se ejecuta en el nodo de desarrollo. El pipeline deploy_dev depende del éxito de checks y solo se ejecuta en push a main con BAKATA_CD_ENABLED=true; no se ejecuta en pull requests. No registra la salida remota en logs públicos.

Antes de habilitar: proteger main (checks requeridos, sin force push ni borrado; definir política de revisión), revisar permisos de escritura y confirmar el subject OIDC real. El repositorio fue creado después de julio de 2026 y el ejemplo usa IDs inmutables. Revisar el ejemplo de confianza y sustituir AWS_ACCOUNT_ID; en el ejemplo de permisos sustituir también MANAGED_INSTANCE_ID. Crear rol dedicado con permiso SendCommand restringido al documento y al nodo, y GetCommandInvocation de solo lectura (AWS no ofrece recurso específico para esa acción). No conceder AWS-RunShellScript ni permisos IAM. El acceso a resultados puede incluir otros comandos de la región; no imprimir secretos en Run Command. Las plantillas son ejemplos, no roles desplegados.

Configurar variables de repositorio BAKATA_DEPLOY_ROLE_ARN y BAKATA_MANAGED_INSTANCE_ID; activar BAKATA_CD_ENABLED únicamente tras completar estos controles y una prueba. El wrapper instalado no se actualiza automáticamente: revisar, validar sintaxis y reinstalar manualmente cambios a scripts/deploy-dev.sh. No guardar claves AWS permanentes.

## Respaldo local de desarrollo
Instalar scripts/backup-dev.sh como /usr/local/sbin/bakata-backup-dev (root:root 0755), e infra/systemd/bakata-backup.{service,timer} en /etc/systemd/system/ (0644). Ejecutar systemctl daemon-reload; systemctl start bakata-backup.service; verificar journalctl -u bakata-backup.service y systemctl enable --now bakata-backup.timer. El timer ejecuta diariamente a las 03:00 Colombia (UTC 08:00), con hasta cinco minutos de dispersión y retención de siete días. Usa el mismo bloqueo que el despliegue. Solo root puede leer /var/backups/bakata; contiene datos y secretos en texto recuperable dentro de archivos comprimidos. No copiar a Git ni publicar. Los backups contienen SQL transaccional, archivos de WordPress, configuraciones seleccionadas y SHA del repositorio. No contienen la clave privada TLS (reemitir el certificado). No son imágenes del servidor. El dump y el tar se ejecutan en momentos distintos; no ofrecen consistencia atómica entre base y archivos durante escrituras. Para restauración, comprobar SHA256SUMS y restaurar primero en un entorno aislado con la misma versión de MariaDB y WordPress. No sobreescribir la tienda activa sin un respaldo previo y plan de recuperación. La validación de integridad no demuestra restaurabilidad; queda pendiente una prueba de restauración aislada y almacenamiento cifrado fuera de Lightsail.

## Disaster recovery: almacenamiento externo
Bucket privado S3 en us-east-1, bloqueo total de acceso público, propiedad del bucket, TLS obligatorio, cifrado SSE-S3 AES-256, versionado habilitado. Prefijo dev/; expiración de versiones actuales a 30 días, no actuales a 7 días y multipart incompletos a 1 día. El rol híbrido de SSM tiene PutObject/AbortMultipartUpload solo en ese prefijo, sin GetObject, DeleteObject ni administración de S3. No usar claves estáticas. Instalar python3-boto3 desde Ubuntu y scripts/upload-backup.py como /usr/local/sbin/bakata-upload-backup (root:root 0755); actualizar el ejecutable root-only de backup desde el commit revisado. El timer existente conserva el horario. El manifiesto SHA256SUMS se sube al final y señala una copia completa; verificar todas las sumas tras descargar. Las cargas parciales no son recuperables. El límite actual es 5 GiB por archivo; migrar a multipart antes de alcanzarlo. La copia local se conserva aunque falle S3; revisar el estado del servicio/journal. S3 versionado sin Object Lock no es inmutable ante un administrador autorizado. No hay réplica multirregional. El cifrado es del lado del servidor, no de extremo a extremo.

### Runbook de recuperación
1. Identificar el prefijo de backup con manifiesto y versiones correctas; usar una identidad de recuperación autorizada, no ampliar permanentemente el rol de escritura. Descargar a directorio privado (0700), comprobar sha256sum -c SHA256SUMS. Nunca imprimir archivos de credenciales o datos personales.
2. Recrear Ubuntu, Docker y configuración mediante el runbook de infraestructura. Recuperar el commit de git-commit y versiones de imágenes anotadas en image-ids; conservar o conseguir imágenes compatibles. Los IDs son locales: para recuperación completa registrar también digests de registro o preservar las imágenes fuera del host.
3. Restaurar SQL en una MariaDB aislada y archivos WordPress en un volumen nuevo, no en la tienda activa. Comprobar core is-installed, plugins activos, tema y consultas de datos. Validar administración y flujos comerciales sin conexiones a proveedores ni pagos.
4. En una recuperación real, restaurar secretos con acceso restringido, reemitir TLS, rotar credenciales si hubo compromiso, probar el sitio con DNS temporal y solo después conmutar DNS o IP. No sobreescribir volúmenes activos.
RPO objetivo diario: hasta 24 h más dispersión/tiempo de ejecución, condicionado a respaldos exitosos. RTO no garantizado; medir en simulacro integral. La copia SQL y la de archivos no son atómicas; antes de producción se requiere una estrategia consistente para cargas y pedidos. No hay alerta externa de fallo todavía.

## Política de ejecuciones CI/CD

Foundation checks se ejecuta en pull requests cuyo destino es main y en cada push a main; no en pushes de ramas de trabajo sin PR. El job checks conserva su nombre y todas sus pruebas, y usa un grupo de concurrencia por PR para cancelar ejecuciones obsoletas del mismo PR. Las validaciones de main tienen grupos independientes por run_id, sin cancelación. El job deploy_dev mantiene íntegros sus requisitos de CI, rama protegida, OIDC y su bloqueo de despliegue sin cancelación de un despliegue activo. No se cambia la configuración de protección de ramas.

Dropify catalog validation mantiene los filtros de rutas y ejecución manual existentes, limita PR a main y cancela únicamente validaciones obsoletas de su propio PR. No comparte grupos con Foundation checks ni cancela ejecuciones manuales. Ningún filtro de rutas se aplica a Foundation checks. GitHub puede mostrar ejecuciones canceladas y la validación de PR no reemplaza la validación del commit integrado en main. Si se modifica un archivo de workflow, revisar los checks requeridos antes de cambiar reglas de protección; no eliminar checks para permitir una fusión.

Para cambios relacionados, crear un único árbol/commit coherente y actualizar la rama una vez; evitar pushes intermedios por archivo, especialmente con un PR abierto. Los workflows ya iniciados con configuración anterior no se cancelan retroactivamente. La reducción de ejecuciones debe observarse tras integrar la configuración en main.
