# Definición independiente del proxy fixture Fargate

`infra/research-aws/proxy-task.json` es una propuesta declarativa independiente que reutiliza la imagen `proxy.Dockerfile` y la red de #82, no un despliegue. Con ambos flags por defecto (`EnableProxyRepository=false`, `EnableProxyTask=false`) no crea recursos de esta plantilla. El repositorio tiene opt-in separado para evitar el ciclo de exigir un digest antes de disponer del repositorio; la tarea exige ambos flags true y un digest SHA-256 no vacío. Activar recursos puede generar costos por imágenes ECR, logs y otros recursos o ejecuciones asociados; la red y endpoints de la foundation son independientes y pueden generar costos incluso si ambos flags son false. El repositorio tiene políticas Retain: desactivar o borrar el stack puede dejarlo retenido con imágenes y costos; revisar y gestionar por separado con autorización. No se ha creado stack, publicado imagen ni ejecutado tarea. El digest identifica una imagen, no demuestra que contenga el código revisado: verificar procedencia, Dockerfile y runtime fixture antes de cualquier ensayo; el diseño de provenance sigue pendiente.

## Bootstrap propuesto, sujeto a aprobación

No es una instrucción para desplegar ahora. Antes de cualquier cambio, acordar un presupuesto explícito, duración, responsable, alertas y plan de retirada, incluyendo ECR retenido, almacenamiento de imágenes, escaneos, logs, endpoints/red y cualquier cómputo; estimar precios según cuenta y región y detenerse si no hay aprobación. Revisar change set y permisos en cada fase.

1. Con autorización separada, crear solo el repositorio con `EnableProxyRepository=true`, `EnableProxyTask=false` y digest vacío. Confirmar que no se crean tarea, role ni logs y registrar el URI real.
2. Construir y revisar la imagen fixture desde fuentes y dependencias aprobadas, sin secretos ni publicación automática. El diseño verificable de provenance aún es pendiente: no promocionar ni usar una imagen hasta resolverlo. Solo tras revisión y autorización explícita, publicar en ese repositorio y obtener y verificar su digest real allí; no usar uno ficticio como trámite.
3. En un change set posterior, mantener ambos flags true y proporcionar ese digest verificado para registrar la definición. Revisar que corresponda al repositorio y que los únicos recursos adicionales sean los previstos. Esto no autoriza ejecución, integración, ni proveedor.

`Retain` significa que desactivar el repositorio o borrar el stack no garantiza eliminarlo; puede quedar fuera de la gestión del stack, con imágenes y facturación, y una reactivación puede crear otro. Inventariar antes y después, acordar conservación y vencimiento, y gestionar cualquier eliminación de repositorio/imágenes solo con autorización específica. Esta secuencia no ha sido probada en AWS.

La definición usa Fargate/awsvpc, un único contenedor UID 65534, raíz de solo lectura y sin capacidades, con execution role dedicado limitado al repositorio proxy y logs propios (el token ECR requiere `*`). No tiene task role, secretos, worker, servicio, balanceador, scheduler, RunTask ni PassRole. El único flag de aplicación fijado es `BAKATA_RESEARCH_PROXY_FIXTURE=1`: deliberadamente faltan el flag de habilitación, bind privado, vencimiento y material mTLS. Por tanto no es ejecutable de extremo a extremo; no introducir certificados o claves reales en el template ni en variables/overrides. La imagen actual no incluye esos archivos. La mera definición tampoco impide que otro principal autorizado registre o ejecute otra tarea: revisar IAM, permisos de overrides y separación administrativa.

La confianza del execution role permite exclusivamente `ecs-tasks.amazonaws.com`, pero todavía no restringe cuenta ni origen. Se deben evaluar las condiciones `aws:SourceAccount` y `aws:SourceArn` contra la documentación vigente y el contexto realmente entregado por ECS para este tipo de rol, región y partición; una condición demasiado estricta podría impedir el pull o los logs. No se presupone que la forma de ARN de una tarea o cluster sea compatible. Validar con revisión IAM y un ensayo autorizado antes de incorporarlas; el lint offline no demuestra su comportamiento. Hasta entonces este punto también es NO-GO.

Para un eventual ensayo expresamente autorizado, usar exclusivamente `ProxyFixtureSubnet` y `ProxyFixtureSecurityGroup` de la foundation #82 para el proxy, y sus correspondientes `ProxyFixtureWorkerSubnet`/`ProxyFixtureWorkerSecurityGroup` para el worker, con `assignPublicIp=DISABLED`, Fargate Linux 1.4.0 o posterior, un proxy por ejecución y sin SG legacy. Una task definition no selecciona ni fuerza subred, SG o IP pública: el futuro controlador y sus permisos deben imponerlos. Revisar rutas efectivas, endpoints, prefix lists y acceso DNS; los SG no bloquean DNS/metadata y no son una frontera completa. Los endpoints de ECR/logs y S3 son para infraestructura, no autorización comercial.

Antes de ejecutar faltan entrega segura y efímera de certificados sintéticos por ejecución, pin y bind, controlador confiable con autorización de ambos ARN y detención/reconciliación, conectividad cliente y pruebas reales de IAM/red/Fargate. Sin estos controles no hay ensayo integrado ni garantía de funcionamiento. El proxy ejecutable de #82 solo conecta a loopback sintético; no habilitar rutas live, secretos reales ni consultas al proveedor. No confundir esta plantilla con aprobación comercial.
