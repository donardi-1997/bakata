# Bakatá Core — preparación de pedidos

OrderPreview es puro y WooOrderPreview es una API interna de lectura mediante CRUD compatible con HPOS, sin invocador comercial, sin REST, cron, UI, cola ni hook de pedidos. Se separa estado WooCommerce de pago/pedido y estado de preparación: el único estado de resultado es preview_only, no enviado ni autorizado. Se requiere processing, fecha de pago, ausencia de reembolsos, total positivo, método distinto de COD y WooCommerce is_paid; esto no confirma liquidación bancaria. No se admiten contraentrega, otros estados, pedidos gratuitos, variaciones, productos virtuales/descargables, eliminados ni destino distinto de CO. La cobertura CO es restricción del escenario, no validación de dirección o entrega. No lee datos personales salvo país de envío, no devuelve destinatario, correo, domicilio, teléfonos, tokens ni datos de pago.

Cada línea requiere mapeo explícito suministrado por llamante con ID de línea histórica, ID de producto, cantidad, proveedor e identidad de fuente. No se infiere un vínculo de metadatos actuales de catálogo, que pueden haber cambiado desde la compra. No existe todavía una persistencia o UI que apruebe tales mapeos; el llamante de pruebas es sintético. Se exige totalidad de líneas, coincidencia de cantidades e IDs, capacidad de edición de pedidos y permiso sobre el objeto. No se divide ni combina cantidades silenciosamente.

La propuesta agrupa por proveedor y ordena grupos/líneas determinísticamente. Referencia SHA-256 de versión, ámbito estable de tienda (debe configurarse y mantenerse único), ID de pedido y proveedor. Huella de contenido separada: cambia si cambian líneas/cantidades o destino; editar una línea no cambia la referencia del grupo. No es idempotencia persistente. Cambiar proveedor puede crear otra referencia; un futuro coordinador debe detectar cambios de asignación en el pedido completo. No reservar ni enviar con estas referencias antes de implementar almacenamiento atómico, validación de huella, bloqueo, gestión de timeout ambiguo y reconciliación con proveedor. No hay cambios de estado, notas, reservas, operaciones financieras ni llamadas externas.

Pruebas: script puro con estados, destinos, duplicados, identidad estable y edición; integración Woo aislada local con pedido histórico sintético, sin checkout ni transacción, permisos, cantidades, lectura, rechazo COD/cancelación y repetición. Se ejecuta después del QA de tienda; volumen CI desechable. No se simula aceptación real del proveedor. Pendientes: evidencia de liquidación según pasarela, mapeo histórico persistente, dirección autorizada y minimización de datos, stock fresco y reservas, validación de costo, contrato de API/sandbox, idempotencia transaccional, estados logísticos persistentes, reintentos y webhook firmado. Envío comercial bloqueado.
