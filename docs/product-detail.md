# Ficha individual de producto

La plantilla single-product usa el bloque legacy-template nativo WooCommerce, dentro de un grupo div (no main duplicado). WooCommerce genera su landmark main, galería, título, precios, descuento, inventario, variantes, cantidad, validación de carrito, descripción, atributos, reseñas, relacionados y datos estructurados. Se habilita el soporte nativo de zoom, slider y lightbox. No se cambian APIs comerciales ni el núcleo. El CSS product.css se acota a bk-product-detail y utiliza los tokens de marca; una columna móvil y dos columnas desde 48rem, pestañas y relacionados debajo. No hay barra de compra fija, para evitar solapamiento en pantalla pequeña.

Información de envíos, cambios/devoluciones y contacto: se reutiliza bakata_footer_links y solo se enlazan páginas publicadas y sin contraseña. No se prometen plazos, cobertura, disponibilidad distinta al inventario ni devoluciones.

QA: fixtures locales después de las suites previas, con un producto simple rebajado, variable con dos opciones (una sin stock), otro agotado y dos imágenes de prueba a partir de un recurso local. Se revisan layout, imágenes, landmark, políticas y axe para simple/variable a 320, 768 y 1440 px. Pruebas de compra parcial en móvil para simple y variación Verde, cantidad 2 e ID mediante Store API; producto agotado sin CTA. No se crean pedidos ni pagos. No se escriben datos en Lightsail. Pendiente validar primera ejecución, interacción específica de ampliación y cambio de imagen, opción agotada en selector, reseñas reales, lector de pantalla, zoom y dispositivos físicos. Las cadenas nativas de WooCommerce siguen el idioma configurado en WordPress; la localización completa a es_CO se validará aparte.

## Recarga tras añadir

La ficha marca sus formularios nativos y, únicamente después de una adición exitosa, usa el filtro de WooCommerce para redirigir el POST a un GET de la ficha. Si WooCommerce está configurado para ir al carrito, conserva esa opción; respeta asimismo una URL de redirección ya establecida por otro filtro. El destino de ficha procede del producto resuelto por el servidor, no de una URL enviada por el navegador. No se modifica WooCommerce.

`qa/product-reload.mjs` es independiente de la suite existente: exige `BAKATA_CI_FIXTURES=1`, limita el destino a HTTP en localhost/127.0.0.1 y bloquea recursos externos. En una instalación Compose **desechable y aislada**, con WooCommerce, el tema y `scripts/product-fixtures-ci.php` ya instalados, ejecutar `BAKATA_CI_FIXTURES=1 BAKATA_QA_URL=http://localhost:PUERTO/ node qa/product-reload.mjs` (por defecto puerto 8080). Requiere las dependencias de `qa` y Chromium de Playwright. Cada caso usa un contexto vacío; añade dos unidades del simple o de la variante Verde, verifica en Store API ID, variación y cantidad, comprueba la cadena POST → 302/303 → GET y vuelve a comparar todo tras recargar mediante GET. Guarda `qa/reports/summary-product-reload.json` y capturas solo ante errores. No pasa por checkout ni proveedores.

Evidencia local, 2026-11-27: Compose con proyecto y volúmenes exclusivos, puerto 18947 y WooCommerce 11.3.1. Antes del cambio, ambos casos devolvían POST 200 sin redirección. Después, ambos pasaron con POST 302 → GET → recarga GET; Store API mantuvo simple ID 12, cantidad 2, y variante ID 14, Color Verde, cantidad 2. Los IDs son específicos de esa instalación. `php -l` del archivo modificado pasó. Esta ejecución no sustituye otras pruebas de ficha ni valida checkout, pasarelas o integraciones.

### Casos negativos y precedencia

En la misma clase de instalación desechable, `qa/product-validation.mjs` fuerza formularios POST para alcanzar la validación del servidor, evitando la validación del navegador: cantidad 6 para el simple y Verde (stock 5), y variable sin selección. Exige aviso visible, respuesta POST 200 sin redirección de éxito y carrito vacío mediante Store API. Para repetir: con las mismas variables locales de la prueba de recarga, `node qa/product-validation.mjs`. El informe es `qa/reports/summary-product-validation.json`.

`scripts/test-product-redirect-ci.php` prueba los filtros reales con WP-CLI y fixtures: por ejemplo, en bash `docker compose -p PROYECTO_DESECHABLE run --rm -T -e BAKATA_CI_FIXTURES=1 cli wp eval "$(tail -n +2 scripts/test-product-redirect-ci.php)"`. Usar también el archivo de entorno y puerto exclusivos de esa instalación. Comprueba marcador ausente, vacío, cero o array, GET, producto inválido o no soportado, URL previa, opción de carrito, filtro anterior y posterior, marcador de catálogo y ambos marcadores. Para probar además la opción de carrito en navegador, configurar esa opción y la página de carrito en la instalación desechable y ejecutar `qa/product-reload.mjs` con `BAKATA_EXPECT_CART_REDIRECT=1` y `BAKATA_EXPECT_CART_PATH=/ruta-del-carrito/`; el informe de recarga se sobrescribe en cada ejecución.

Ambos filtros del tema están registrados a prioridad 10: catálogo se carga primero y ficha después. El filtro de ficha conserva una URL ya elegida; un filtro a prioridad 20 puede reemplazarla. El comportamiento preexistente de catálogo es diferente: su marcador válido fuerza el carrito incluso si había una URL previa. Con ambos marcadores válidos, catálogo decide primero y ficha conserva ese destino; no se ha cambiado ese comportamiento. La prueba de prioridad describe la configuración del tema, no garantiza que extensiones externas no añadan filtros que cambien el resultado.

Evidencia adicional local, 2026-11-27, WooCommerce 11.3.1: 15 casos sintéticos aprobados; tres rechazos de validación/stock con carrito vacío; recarga de simple y variante aprobada tanto volviendo a ficha como con la opción de carrito activa (POST 302 → GET del carrito → GET de recarga, cantidad 2 e ID/variación sin cambios). La ruta efectiva del carrito de prueba era `/cart-2/`. El proyecto y sus volúmenes fueron desechados; no se modificó CI.

**Límite:** POST/Redirect/GET evita repetir una adición exitosa al recargar el documento GET; no es una clave de idempotencia ni impide dos clics, dos POST concurrentes, reintentos de red o envíos en pestañas distintas. Los POST rechazados permanecen en la respuesta de error nativa y no se garantiza que recargar esa respuesta evite un nuevo envío. No se probaron concurrencia, pagos ni proveedores.
