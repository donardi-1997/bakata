# Bakatá Core — protocolo de referencia y recibos persistentes

Fase de seguridad interna, sin ruta REST pública, webhook de proveedor, cron, cola, envío comercial, actualización de fulfillment ni configuración de secretos. El protocolo v1 es sintético y NO representa la especificación de ningún proveedor. Se deberá implementar y probar la firma real de la API elegida. La clase SignedEvent valida un alcance de tienda/proveedor/cuenta proveniente de configuración confiable, key ID, clave de al menos 32 bytes, timestamp Unix decimal de 10 dígitos, ventana explícita de 1 a 600 segundos, cuerpo máximo 16 KiB y firma v1=hex HMAC-SHA256. Firma el JSON de la lista [bakata-webhook-v1, tienda, proveedor, cuenta, keyId, timestamp, SHA256 del cuerpo exacto], verifica con hash_equals antes de decodificar y exige esquema cerrado y tiempo UTC de segundos, no futuro ni posterior a la firma. El remitente debe re-firmar reintentos fuera de ventana. La clave no se persiste ni se registra; los parámetros sensibles se marcan SensitiveParameter. La configuración debe resolver la clave por alcance y key ID de forma confiable; no se implementa gestión de claves.

WebhookInbox registra explícitamente la vinculación de un grupo de OrderPreview con alcance, referencia y huella; no prueba autorización, no autoriza despacho y no valida que el grupo sea genuino sin un llamante confiable. Vinculación por tienda+referencia: cambiar proveedor/cuenta/contenido produce conflicto. El evento autenticado debe coincidir con una vinculación existente. Dedupe por tienda/proveedor/cuenta/eventId, independiente del key ID para preservar rotación. Huella del evento normalizado (no de firma, espacio JSON ni orden de campos). Mismo ID con contenido diferente se rechaza. La recepción no ejecuta máquina de estados ni verifica transiciones o cronología entre eventos. Solo devuelve recorded/duplicate. Duplicate significa recibido previamente, NO procesado o despachado.

WpReceiptLedger usa tabla propia prefijo + bakata_receipts_v1 (InnoDB), PK ascii binaria de hash, huella, token aleatorio de inserción y época de recepción. Inserción única con ON DUPLICATE KEY UPDATE sin mutación, lectura de huella/token distingue primero/repetido y conflicto; no se basa en filas afectadas. No usa SQL de pedidos, no guarda cuerpo, datos personales, guía ni secreto. Las huellas son datos pseudonimizados, no anonimización; acceso y retención deberán definirse. Instalación explícita requiere manage_options; verifica motor y PK, no se llama automáticamente ni crea tabla en Lightsail al cargar plugin. El llamante futuro debe garantizar esquema íntegro/versionado y permisos del servicio. No hay política de borrado: retención debe cubrir reintentos y conflictos; nunca borrar automáticamente recibos activos. No hay rollback de acciones externas ni garantía exactamente una vez. No se persiste el evento íntegro ni hay reanudación de procesamiento: falta inbox/outbox de trabajo con estado, payload mínimo protegido, concurrencia y transacción con aplicación de efecto. La operación de registro no inicia un pedido. No se implementa aún reintento de despacho, ni automatización. CI usa memoria para protocolo y MariaDB local para recibos, replay entre instancias, conflicto y minimización. Recuperación de fallo pendiente. Producción bloqueada hasta validar proveedor, esquema/migraciones, secretos/rotación, endpoint con permisos, límites de tráfico, persistencia de trabajo y reconciliación de timeouts. No se modifica WooCommerce ni configuración comercial.

## Carrera aislada y reproducible

`scripts/test-webhook-ledger-race.php` está destinado exclusivamente al Compose desechable `scripts/compose-receipt-race.yaml`, sin puertos publicados y con red Docker interna, base y volúmenes nuevos. El proceso principal y cada worker comprueban destino `db:3306`, resolución IPv4 no pública, nombre de base y marca aleatoria provisionada en esa base. La marca es una protección contra ejecución accidental, no una prueba criptográfica de ubicación: DNS privado, marca o configuración podrían falsificarse; no ejecutar fuera de este Compose ni con demonio Docker remoto o infraestructura no confiable. Crea claves sintéticas aleatorias sin borrar filas existentes. En cada ronda arranca ocho procesos PHP, comprueba IDs de conexión distintos y libera una barrera solo cuando todos están listos. Cinco rondas usan la misma huella y otras cinco alternan dos huellas: se exige una fila, un `recorded` y que cada otro resultado sea `duplicate` o conflicto según la huella almacenada. La espera activa tiene límites de 30 segundos para estar listos y 30 para terminar; ante error intenta terminar los hijos creados y elimina solo archivos temporales propios. Son límites de esas esperas, no una garantía de terminación global: conexiones, llamadas de sistema, `proc_close`, Docker y limpieza pueden bloquearse. No necesita WooCommerce ni activa rutas, pedidos o integraciones.

Desde la raíz, con Bash, Docker Compose local y `openssl`:

```sh
bash scripts/run-webhook-ledger-race.sh
```

El wrapper rechaza `DOCKER_HOST` y `DOCKER_CONTEXT` definidos, inspecciona el endpoint del contexto activo y fija ese contexto para las llamadas posteriores. Solo admite el socket Unix estándar `/var/run/docker.sock` existente o el named pipe local de Docker Desktop Linux `npipe:////./pipe/dockerDesktopLinuxEngine`; otros endpoints, incluso túneles SSH/TCP, se rechazan. Esto verifica la ruta declarada, no que un proxy en el socket, un daemon o su configuración no reenvíen a otro lugar: solo usar Docker local confiable.

Genera un nombre y una etiqueta de propiedad aleatorios, enumera recursos y nombres esperados antes de crear y falla cerrado si Docker no responde. Hay una ventana TOCTOU entre enumeración y creación; el nombre aleatorio reduce colisiones accidentales pero no protege contra actores que intervengan o manipulen etiquetas. Espera hasta 90 segundos por los archivos de WordPress y conserva el código de fallo de la prueba aunque falle la limpieza. En salida normal, error, SIGINT o SIGTERM intenta eliminar únicamente recursos con ambas etiquetas del proyecto y del token; si no puede verificar propiedad, no elimina. Durante limpieza ignora otras señales SIGINT/SIGTERM para no interrumpirla a medias; SIGKILL, cierre abrupto o Docker bloqueado pueden dejar recursos. Si falla la limpieza, informa el proyecto para inspección manual. La espera de readiness se comprueba entre invocaciones de Docker y no limita una llamada de Docker bloqueada. Las contraseñas, correo y URL son sintéticos; no se publica ningún puerto.

El wrapper valida por separado que cada llamada a `openssl` termine correctamente y produzca el hexadecimal de longitud esperada antes de consultar Docker o crear recursos. `bash scripts/test-run-webhook-ledger-race.sh` prueba con comandos simulados fallos y valores inválidos del generador, rechazo de endpoint remoto y de ambos overrides, errores de contexto y enumeración, colisiones, selección de recursos propios, conservación del código de fallo, error de limpieza y éxito; no crea recursos Docker. Los endpoints aceptados siguen siendo deliberadamente conservadores: otras configuraciones locales deben adaptarse y verificarse antes de usarse.

Evidencia local del 27-11-2026: Docker Desktop, imágenes `mariadb:11.4`, `wordpress:php8.3-apache` y `wordpress:cli-php8.3`; wrapper con proyecto, red interna y volúmenes nuevos, sin puerto publicado. Las diez rondas (80 invocaciones) pasaron las comprobaciones y, en otra ejecución aislada, una marca incorrecta fue rechazada. La barrera coordina el inicio pero **no demuestra solapamiento ni contención real de las sentencias**, ni explora todos los intercalados; no se probaron caída durante inserción/lectura, particiones, failover ni recuperación. El resultado es evidencia limitada de deduplicación del registro, no de procesamiento o efectos externos exactamente una vez.
