# Bakatá Core — protocolo de referencia y recibos persistentes

Fase de seguridad interna, sin ruta REST pública, webhook de proveedor, cron, cola, envío comercial, actualización de fulfillment ni configuración de secretos. El protocolo v1 es sintético y NO representa la especificación de ningún proveedor. Se deberá implementar y probar la firma real de la API elegida. La clase SignedEvent valida un alcance de tienda/proveedor/cuenta proveniente de configuración confiable, key ID, clave de al menos 32 bytes, timestamp Unix decimal de 10 dígitos, ventana explícita de 1 a 600 segundos, cuerpo máximo 16 KiB y firma v1=hex HMAC-SHA256. Firma el JSON de la lista [bakata-webhook-v1, tienda, proveedor, cuenta, keyId, timestamp, SHA256 del cuerpo exacto], verifica con hash_equals antes de decodificar y exige esquema cerrado y tiempo UTC de segundos, no futuro ni posterior a la firma. El remitente debe re-firmar reintentos fuera de ventana. La clave no se persiste ni se registra; los parámetros sensibles se marcan SensitiveParameter. La configuración debe resolver la clave por alcance y key ID de forma confiable; no se implementa gestión de claves.

WebhookInbox registra explícitamente la vinculación de un grupo de OrderPreview con alcance, referencia y huella; no prueba autorización, no autoriza despacho y no valida que el grupo sea genuino sin un llamante confiable. Vinculación por tienda+referencia: cambiar proveedor/cuenta/contenido produce conflicto. El evento autenticado debe coincidir con una vinculación existente. Dedupe por tienda/proveedor/cuenta/eventId, independiente del key ID para preservar rotación. Huella del evento normalizado (no de firma, espacio JSON ni orden de campos). Mismo ID con contenido diferente se rechaza. La recepción no ejecuta máquina de estados ni verifica transiciones o cronología entre eventos. Solo devuelve recorded/duplicate. Duplicate significa recibido previamente, NO procesado o despachado.

WpReceiptLedger usa tabla propia prefijo + bakata_receipts_v1 (InnoDB), PK ascii binaria de hash, huella, token aleatorio de inserción y época de recepción. Inserción única con ON DUPLICATE KEY UPDATE sin mutación, lectura de huella/token distingue primero/repetido y conflicto; no se basa en filas afectadas. No usa SQL de pedidos, no guarda cuerpo, datos personales, guía ni secreto. Las huellas son datos pseudonimizados, no anonimización; acceso y retención deberán definirse. Instalación explícita requiere manage_options; verifica motor y PK, no se llama automáticamente ni crea tabla en Lightsail al cargar plugin. El llamante futuro debe garantizar esquema íntegro/versionado y permisos del servicio. No hay política de borrado: retención debe cubrir reintentos y conflictos; nunca borrar automáticamente recibos activos. No hay rollback de acciones externas ni garantía exactamente una vez. No se persiste el evento íntegro ni hay reanudación de procesamiento: falta inbox/outbox de trabajo con estado, payload mínimo protegido, concurrencia y transacción con aplicación de efecto. La operación de registro no inicia un pedido. No se implementa aún reintento de despacho, ni automatización. CI usa memoria para protocolo y MariaDB local para recibos, replay entre instancias, conflicto y minimización. Prueba de carrera multiproceso y recuperación de fallo pendientes. Producción bloqueada hasta validar proveedor, esquema/migraciones, secretos/rotación, endpoint con permisos, límites de tráfico, persistencia de trabajo y reconciliación de timeouts. No se modifica WooCommerce ni configuración comercial.
